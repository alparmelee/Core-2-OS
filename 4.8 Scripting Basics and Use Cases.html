Part A

Script file types

Common script extensions across Windows, Linux, and cross-platform environments.

.bat — Windows Batch file

Batch script

Executed at the command line, dating back to DOS and OS/2. Uses simple sequential commands (echo, copy, del, net use) and is still widely used for basic Windows automation tasks.

.ps1 — PowerShell script

Used primarily by Windows system administrators, leveraging built-in functions called cmdlets to access and modify operating system parameters and Active Directory.

More powerful than batch files — supports pipelines, object manipulation, and remote management. Execution policy may restrict running unsigned scripts.

.vbs — Visual Basic Script

VBScript — Microsoft Visual Basic Scripting Edition

Used for desktop scripting, backend web server operations, and Microsoft Office macros. Runs through the Windows Script Host (wscript.exe or cscript.exe).

Legacy technology — largely replaced by PowerShell, but still appears in older automation and macro environments.

.sh — Unix/Linux shell script

Identified by a shebang or hashbang (#!) on its initial line, which specifies the interpreter — for example #!/bin/bash or #!/bin/sh.

Common on macOS and Linux for system administration, cron jobs, and deployment pipelines.

.js — JavaScript

Used to enable dynamic interactivity within web browsers — distinct from the Java programming language despite the similar name.

Also runs server-side via Node.js for automation, build tools, and API integrations. Browser JavaScript and server-side Node.js serve different roles.

.py — Python script

Provides cross-platform compatibility across Windows, macOS, Linux, and cloud-based automation. Popular for IT automation, data collection, and infrastructure-as-code tooling.

Readable syntax and extensive libraries make Python a common choice for scripting tasks that span multiple operating systems.

Part B

Use cases for scripting

Why organizations automate tasks with scripts instead of performing them manually.

Basic automation

Handles repetitive or mundane tasks at high execution speeds without requiring manual input or direct oversight — freeing technicians for complex troubleshooting.

Restarting machines

Triggers remote system reboots following application updates or security patches, or schedules periodic reboots to clear hardware memory leaks.

Remapping network drives

Automatically maps shared network drives during user login, repository updates, or backup processes — ensuring consistent drive letters across the organization.

Installation of applications

Automates software deployments by mapping installation drives, running setup routines with pre-filled prompts, and initiating post-install reboots — standard in enterprise imaging and SCCM/Intune deployments.

Automated backups

Executes resource-intensive data transfers to backup drives during off-peak hours, minimizing impact on user productivity and network bandwidth.

Gathering of information and data

Automates system monitoring, hardware and software inventory collection, and vulnerability scanning using protocols like SNMP.

Initiating updates

Deploys operating system patches, application upgrades, and updated hardware device drivers without user intervention — critical for maintaining security posture at scale.

Part C

Other considerations when using scripts

Risks and best practices before running or deploying scripts in production environments.

Unintentionally introducing malware

Running unverified installation scripts or deploying infected software files can inadvertently distribute malware across networked endpoints.

Always review script source, verify checksums, and test in an isolated sandbox before wide deployment.

Inadvertently changing system settings

Unintended registry modifications or configuration edits can break system resources, requiring thorough pre-deployment testing and rollback scripts.

Document every change a script makes and maintain version control so you can revert quickly.

Browser or system crashes due to mishandling of resources

Syntax errors, loose characters, or logical bugs within scripts can cause resource exhaustion, service outages, or system downtime.

Test scripts on non-production systems first. Include error handling, logging, and exit codes so failures are visible rather than silent.
